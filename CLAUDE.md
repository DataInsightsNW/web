# Data Insights North West — website

The live marketing site for Aaron's own data-analysis business, deployed to GitHub Pages at
<https://datainsightsnorthwest.co.uk>. This is the working clone of the `datainsightsnw/web`
repository — the repo root *is* the deployed site.

## Not Markel work

Nothing from this project goes into the `Markel Direct Tech & Sales - Documents` SharePoint
library. It is a separate business, a self-contained git repo, and can be moved out of corporate
OneDrive whenever Aaron wants. Keep accounts separate too: commits use the personal address
`aaronchadburn30@outlook.com`, set as repo-local git config, not the Markel one.

## The repository is PUBLIC

Anything committed here is publicly browsable on GitHub, whether or not GitHub Pages serves it.
`paperwork/` (retainer, invoice and quote templates) and `_docs/` (handover notes) are therefore
**gitignored and local only**. Don't commit them, and don't put client data, real customer
figures, or credentials anywhere in this tree.

The Web3Forms `access_key` in `contact.html` is a public form identifier, not a secret — it is
meant to be in client-side HTML.

## Structure — the thing to get right

**`_src/` is the source of truth. The HTML files at the repo root are GENERATED by
`_tools/Build-Site.ps1` and overwritten on every run.** Never edit a root `.html` file — the
change is silently lost on the next build. Every generated file says so on line 2.

- `_src/partials/` — `head`, `header`, `footer`, `tail`, shared by every page (`{{TOKEN}}` substitution)
- `_src/pages/` — one file per page: a metadata comment block, then the `<main>` content
- `_src/assets/` — `styles.css`, `main.js`, copied to `assets/`
- `_src/brand/` — logo and favicon SVGs (`favicon.svg` and `logo.svg` land at the root, the rest in `assets/`)
- `_src/static/` — `robots.txt`, copied to the root
- `_tools/` — the build script, the QA checker, the asset rasteriser

The `_`-prefix matters: GitHub Pages runs Jekyll, and Jekyll never publishes a folder starting
with `_`. That is why the source and tooling can live in the same repo as the deployed site
without being served or indexed. **Do not add a `.nojekyll` file** — that would disable Jekyll
and start publishing `_src/`.

## Workflow

```powershell
.\_tools\Build-Site.ps1     # _src/ -> repo root, regenerates sitemap.xml
py .\_tools\qa.py            # must print ALL CHECKS PASS before pushing
```

`Build-Site.ps1` fails loudly on an unreplaced `{{TOKEN}}` or missing page metadata.
`qa.py` checks internal links resolve, JSON-LD parses, canonicals match their own URL, head tags
are present, no `<mark class="todo">` survives, every class used exists in `styles.css`, one
`<h1>` per page, and sitemap membership agrees with each page's robots meta.

`py .\_tools\render-assets.py` regenerates the three PNGs that cannot be SVG — the social share
card, the apple-touch-icon, and the wordmark lockup for directories and email signatures. It
drives headless Chrome so the webfonts are actually applied. Only re-run it if the brand or the
card copy changes.

To preview locally, root-relative asset paths mean you need a server, not `file://`:

```powershell
py -m http.server 8731        # then http://127.0.0.1:8731/
```

## Never move or delete these

| File | Why |
|---|---|
| `CNAME` | Holds `datainsightsnorthwest.co.uk`. Deleting it drops the custom domain and the site reverts to the github.io URL |
| `googlea4b8db69c89cd24d.html` | Google Search Console verification. Deleting it un-verifies the property and the sitemap stops being read |

Neither is generated by the build, and `Build-Site.ps1` has both on a `$Protected` list so a page
slug can never collide with them.

## Conventions

- **The logo mark is the letter W of "North West", drawn as a data line, sitting on a gold axis
  rule.** Both halves are load-bearing: the zigzag is the initial *and* a chart, and the rule is
  what stops it reading as merely a letter. Don't remove the rule, don't swap it for a dot, and
  don't replace the mark with bars — ascending bars is the most generic logo in the analytics
  category, which is what this replaced. Geometry is symmetric and tuned for 16px; the open
  version (header, lockup) and the tiled version (favicon, avatar, app icon) must stay in step,
  and the tile lives in three places: `_src/brand/favicon.svg`, `_src/partials/header.html` /
  `footer.html` (inline), and `MARK_TILE` in `_tools/render-assets.py`.
- Colours and type are tokens at the top of `_src/assets/styles.css`. Restyle there, never inline.
- **Colour must carry meaning.** Green = primary/interactive/positive, amber = the "before" or
  manual state, red = loss or error. The stylesheet this replaced had alternating green/amber
  card borders and gradient fills that meant nothing, which is what made the site read as
  amateur. Don't reintroduce decorative colour.
- Chart palette is **validated**, not chosen by eye — see the comment block at the top of
  `styles.css` for the categorical and sequential values and their measured CVD separation.
  Re-run the validator in the `dataviz` skill if you change a series colour.
- `#D98A2B` amber sits at 2.76:1 against white, below the 3:1 bar. It is legal only because
  every use carries a direct text label. Keep it that way.
- All internal links are **root-relative** (`/services.html`), which is what lets
  `insights/` articles share one set of asset paths.
- Single theme by design: no dark mode. `body` paints its own background explicitly.
- Every sample figure on the site must **reconcile**. On the examples page the three regions sum
  to the monthly totals, which sum to the 12-month revenue, and revenue ÷ orders gives the stated
  average order. On a data analyst's own website a sum that doesn't tie is the worst possible
  detail to get wrong — check the arithmetic before changing any number.
- All sample data is invented and must stay clearly labelled as illustrative. Client work is
  never published as an example.

## Content rules

1. **Never invent credentials.** No qualifications, certifications, years of experience, former
   employers, client names, client counts, testimonials, reviews, awards, memberships, company
   number or VAT number. The business is new and has no published client work. If a value isn't
   known, leave a `<mark class="todo">` placeholder — `qa.py` fails the build on those, so one
   can't be published unnoticed.
2. **No promised outcomes.** Describe what the work does, not results guaranteed.
3. **Keep the sample-data disclosure** on every mockup, and the note at the top of
   `examples.html`.
4. **No analytics or tracking without updating `privacy.html` first.** The site currently sets no
   cookies, which is why it needs no cookie banner, and `privacy.html` and the FAQ both say so.
   Adding anything that tracks visitors makes both statements false.
5. British English, and the business voice is **first person singular — "I", not "we"**. It's a
   sole trader, and "we" reads as a fake agency. Two exceptions, both deliberate:
   - **Client voice stays plural.** FAQ `<summary>` questions and their JSON-LD `"name"` fields
     are the client asking ("Is our data kept confidential?"), as is quoted client speech
     ("our reporting is a mess"). Never switch those.
   - Watch to-be agreement: "I am", never "I are".
   `_tools/switch-voice.py` did the original conversion and documents the masking rules if a
   bulk change is ever needed again.

## After adding or renaming a page

1. Add it to `_src/partials/header.html` (nav) and/or `_src/partials/footer.html`.
2. Rebuild, then run `qa.py`.
3. `sitemap.xml` is regenerated automatically — never hand-edit it.
4. Re-submit the sitemap in Google Search Console (Sitemaps → enter `sitemap.xml` → Submit).
   Google re-reads a submitted sitemap on its own schedule, so this only speeds discovery up.
